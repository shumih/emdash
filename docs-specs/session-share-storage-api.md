# Session Share Storage API — спецификация

Требование к внешнему HTTP‑сервису, который хранит расшаренные сессии CLI‑агентов и
**конвертирует** их между тремя форматами: **Claude Code**, **Codex**, **Cursor**.

Приложение (emdash/tondash) само форматы не конвертирует. Оно:

- при шаринге — читает сырой транскрипт сессии на диске, кодирует в base64, помечает
  провайдером‑источником и **сохраняет** в этот сервис;
- при применении — **запрашивает** ту же сессию у сервиса, указывая нужный целевой
  формат, и пишет полученные байты в каталог соответствующего CLI.

Вся конвертация Claude ↔ Codex ↔ Cursor выполняется **на стороне сервиса**.

> Этот контракт уже реализован на стороне клиента в
> `src/main/core/shared-sessions/http-store.ts` и `src/shared/shared-sessions.ts`.
> Сервис должен ему соответствовать дословно.

---

## 1. Базовые принципы

| Свойство | Значение |
|---|---|
| Транспорт | HTTP/HTTPS, JSON (`application/json; charset=utf-8`) |
| База URL | настраивается пользователем (`Settings → Integrations`), без хвостовых `/` |
| Аутентификация | `Authorization: Bearer <token>` (опционально, см. §3) |
| Кодирование файлов | всегда **base64** (binary‑safe; важно для бинарного `store.db` Cursor) |
| Идемпотентность | сохранение идемпотентно по `shareId` (см. §6) |
| Конвертация | на стороне сервиса, при запросе `GET` с параметром `target` |

Провайдеры обозначаются строкой: `"claude" | "codex" | "cursor"`.

---

## 2. Модель данных

### 2.1 `RawFile`

Один файл транскрипта, закодированный в base64.

```jsonc
{
  "relName": "0a1b2c3d-....jsonl",   // basename файла; информативно
  "base64":  "eyJ0eXBlIjoidXNlciJ9..." // содержимое файла, base64
}
```

### 2.2 `RawBundle`

Сырой транскрипт одной сессии с тегом провайдера. Сейчас у всех трёх провайдеров
сессия — это **один файл**, поэтому `files` обычно содержит один элемент (поле
сделано массивом на будущее).

```jsonc
{
  "provider": "claude",            // "claude" | "codex" | "cursor" — формат файлов ниже
  "files": [ { "relName": "...", "base64": "..." } ],
  "meta": {
    "sourceSessionId": "0a1b2c3d-....", // нативный session id источника
    "cwd": "/Users/me/projects/app",     // рабочая директория (нужна для Claude)
    "title": "Fix auth bug",             // человекочитаемое имя (опц.)
    "model": "claude-opus-4-7"           // опц.
  }
}
```

### 2.3 Ответ сохранения — `SaveResult`

```jsonc
{
  "ref": "abc123",                          // ОБЯЗАТЕЛЬНО: непрозрачная ссылка
  "url": "https://share.example.com/s/abc123" // опц.: человекочитаемая ссылка
}
```

`ref` — единственный идентификатор, по которому потом запрашивается сессия. Формат
произвольный (id, slug, подписанный токен), главное — стабильный и URL‑safe или
корректно проходящий `encodeURIComponent`.

---

## 3. Аутентификация

- Если пользователь задал токен, клиент шлёт `Authorization: Bearer <token>` на **все**
  запросы.
- Если токен не задан, заголовок не отправляется. Сервис вправе требовать токен и
  отвечать `401`.
- Рекомендуется привязывать `ref` к владельцу/токену и не отдавать чужие сессии.

---

## 4. Эндпоинты

### 4.1 `POST /sessions` — сохранить (и поставить в очередь на конвертацию)

Сохраняет сырой бандл. Сервис обязан уметь по нему отдать сессию в любом из трёх
форматов (см. §5). Конвертацию допустимо делать лениво при `GET` или заранее.

**Запрос**

```
POST {base}/sessions
Authorization: Bearer <token>        // если задан
Content-Type: application/json
```

```jsonc
{
  "shareId": "f81d4fae-7dec-11d0-a765-00a0c91e6bf6", // ключ идемпотентности (UUID)
  "bundle":  { /* RawBundle, см. §2.2 */ }
}
```

**Ответ `200 OK`**

```jsonc
{ "ref": "abc123", "url": "https://share.example.com/s/abc123" }
```

- Тело ответа **обязано** содержать `ref`. Клиент копирует `url ?? ref` в буфер обмена.
- Идемпотентность: повторный `POST` с тем же `shareId` должен вернуть **тот же `ref`**
  и заменить содержимое (а не создать дубль). См. §6.

**Ошибки:** любой не‑2xx статус клиент трактует как ошибку загрузки и показывает
сообщение `Share upload failed: <status>`.

---

### 4.2 `GET /sessions/{ref}?target=<provider>` — получить в нужном формате

Возвращает сессию, **сконвертированную** в формат `target`. Если `target` совпадает с
исходным провайдером — вернуть исходные байты без потерь.

**Запрос**

```
GET {base}/sessions/{ref}?target=claude
Authorization: Bearer <token>        // если задан
```

`ref` проходит через `encodeURIComponent`. `target` ∈ `{claude, codex, cursor}`.

**Ответ `200 OK`** — `RawBundle` (см. §2.2), где `provider` равен `target`, а `files`
содержат уже сконвертированный транскрипт в формате целевого провайдера.

```jsonc
{
  "provider": "claude",
  "files": [ { "relName": "imported.jsonl", "base64": "..." } ],
  "meta": { "sourceSessionId": "<исходный>", "title": "Fix auth bug" }
}
```

**Ответ `404 Not Found`** — сессия не найдена/истекла. Клиент трактует это как
«сессии нет» (а не как ошибку) и сообщает пользователю.

**Прочие не‑2xx** — клиент показывает `Share fetch failed: <status>`.

> Замечание про `relName`: на применении клиент сам вычисляет путь записи по
> `target`‑провайдеру (см. §5), поэтому `relName` информативен. Содержимое `base64`
> должно быть валидным файлом целевого формата.

---

### 4.3 (Опционально) вспомогательные методы

Не требуются клиентом сейчас, но желательны для эксплуатации:

- `HEAD /sessions/{ref}` — проверка существования.
- `DELETE /sessions/{ref}` — удаление (отзыв ссылки).
- `GET /healthz` — liveness.

## 5. Форматы провайдеров (что приходит и что нужно произвести)

Каждый бандл — один файл. Ниже — реальная структура исходных файлов; конвертер должен
парсить источник и порождать корректный файл целевого провайдера.

### 5.1 Claude Code — `claude`

- **Файл:** `<session-id>.jsonl` (на клиенте лежит в
  `~/.claude/projects/<enc-cwd>/<session-id>.jsonl`).
- **Формат:** JSONL — по одному JSON‑объекту в строке, событие на строку.
- **Типы строк** (`type`): `user`, `assistant`, `attachment`,
  `file-history-snapshot`, `permission-mode` и др.
- **Связность:** цепочка через `parentUuid`; полезная нагрузка в
  `message: { role, content[] }`; tool‑вызовы внутри `content`.
- Поля строки: `uuid`, `timestamp` (ISO), `sessionId`, `cwd`, `version`, `gitBranch` и т.п.

### 5.2 Codex — `codex`

- **Файл:** `rollout-<ts>-<uuid>.jsonl` (на клиенте — в
  `~/.codex/sessions/YYYY/MM/DD/`).
- **Формат:** JSONL. Первая строка — `type: "session_meta"`
  (`payload.id`, `cwd`, `cli_version`, `base_instructions`…). Далее строки
  `type: "response_item"` (`payload.type:"message"` с `role` и
  `content[{type:"input_text"|"output_text", text}]`), `event_msg`, `turn_context`.
- (`~/.codex/history.jsonl` — это только список промптов, **не** сессия; не использовать.)

### 5.3 Cursor — `cursor`

- **Файл:** `store.db` (на клиенте — в `~/.cursor/chats/<chatId>/<agentId>/store.db`).
- **Формат:** **бинарный SQLite**, content‑addressable blob store:
  - таблица `meta(key, value)` — JSON со ссылкой `latestRootBlobId`, `agentId`, `name`…;
  - таблица `blobs(id, data)` — `id = sha256(data)`; корневой блоб — protobuf‑список
    32‑байтных хэшей дочерних блобов; листовые блобы — JSON `{role, content, …}`.
- Поскольку файл бинарный, он передаётся как есть через `base64`. При конвертации
  **в** Cursor сервис должен собрать валидный `store.db` (пересчитать sha256‑блобы и
  `meta`); при конвертации **из** Cursor — обойти blob‑DAG и извлечь сообщения.

### 5.4 Матрица конвертации и потери

- Конвертация **lossy**. Перенос полного транскрипта (user/assistant/tool) — best effort.
- Особо отметить: Cursor ↔ (Claude/Codex) теряет большинство tool‑вызовов; Cursor как
  цель требует сборки protobuf‑DAG + sha256.
- `target == provider источника` ⇒ вернуть исходные байты без изменений (lossless).
- Рекомендуется хранить исходный бандл и конвертировать «на лету», чтобы любая пара
  была доступна без потери исходника.

---

## 6. Идемпотентность

- Ключ идемпотентности сохранения — `shareId` (UUID), который клиент генерирует
  **детерминированно** из conversation id (повторный шаринг той же сессии присылает
  тот же `shareId`).
- Требование: `POST /sessions` с уже виденным `shareId` обязан вернуть **тот же `ref`**
  и **заменить** содержимое, не плодя дублей.
- Следствие: `ref` должен быть стабильной функцией от `shareId` (либо хранимым
  отображением `shareId → ref`).

---

## 7. Коды ответов

| Код | Когда | Реакция клиента |
|---|---|---|
| `200` | успех save/get | обрабатывает тело |
| `400` | некорректный бандл/таргет | ошибка загрузки |
| `401`/`403` | нет/неверный токен | ошибка |
| `404` | `GET` несуществующего `ref` | «сессии нет» (не ошибка) |
| `409` | конфликт идемпотентности | следует избегать — вернуть `200` с тем же `ref` |
| `413` | слишком большой бандл | ошибка |
| `5xx` | сбой сервиса/конвертации | ошибка |

Тело ошибки желательно в виде `{ "error": "<человекочитаемо>" }` (клиент сейчас
использует только статус, но текст помогает в диагностике).

---

## 8. Ограничения и нефункциональные требования

- **Размер.** Клиент читает транскрипт целиком в память (лимит чтения ~64 МБ) и
  отказывается шарить усечённый файл. Сервис должен принимать тело хотя бы до ~64 МБ
  (с запасом на base64 ≈ +33%, т.е. ~85 МБ JSON). Заложить разумный максимум и `413`.
- **Приватность.** Транскрипты содержат исходный код и потенциально секреты.
  Хранить зашифрованно; `ref` делать неугадываемым; поддержать TTL/`DELETE`.
- **Конвертация — детерминированная** для одного источника и `target` (желательно), чтобы
  повторные `GET` были стабильны.
- **Идемпотентность сети.** `GET` идемпотентен и безопасно ретраится; `POST` —
  идемпотентен по `shareId`.

---

## 9. Версионирование

- Рекомендуется префикс версии в пути: `/{v1}/sessions`. Текущий клиент использует
  базовый URL «как есть», поэтому версия может входить в настроенный `endpointUrl`
  (например, `https://share.example.com/v1`).
- При расширении `RawBundle` сохранять обратную совместимость полей `meta`.

## 10. Примеры

### 10.1 Сохранить Claude‑сессию

```http
POST /v1/sessions HTTP/1.1
Host: share.example.com
Authorization: Bearer sk_live_...
Content-Type: application/json

{
  "shareId": "f81d4fae-7dec-11d0-a765-00a0c91e6bf6",
  "bundle": {
    "provider": "claude",
    "files": [{ "relName": "sess.jsonl", "base64": "eyJ0eXBlIjoidXNlciJ9Cg==" }],
    "meta": { "sourceSessionId": "sess", "cwd": "/Users/me/app", "title": "Fix auth" }
  }
}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "ref": "abc123", "url": "https://share.example.com/s/abc123" }
```

### 10.2 Получить ту же сессию как Codex

```http
GET /v1/sessions/abc123?target=codex HTTP/1.1
Host: share.example.com
Authorization: Bearer sk_live_...
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "provider": "codex",
  "files": [{ "relName": "rollout-imported.jsonl", "base64": "eyJ0eXBlIjoic2Vzc2lvbl9tZXRhIn0K..." }],
  "meta": { "sourceSessionId": "sess", "title": "Fix auth" }
}
```

### 10.3 Сессия не найдена

```http
GET /v1/sessions/nope?target=claude HTTP/1.1
```

```http
HTTP/1.1 404 Not Found
```

## 11. Чек‑лист реализации сервиса

- [ ] `POST /sessions` принимает `{ shareId, bundle }`, идемпотентен по `shareId`, отдаёт `{ ref, url? }`.
- [ ] `GET /sessions/{ref}?target=<provider>` отдаёт `RawBundle` в формате `target` или `404`.
- [ ] Парсеры источников: Claude JSONL, Codex rollout JSONL, Cursor SQLite blob‑store.
- [ ] Сериализаторы целей: те же три формата; `target == source` — lossless.
- [ ] Bearer‑аутентификация и изоляция доступа по владельцу `ref`.
- [ ] Лимиты размера, шифрование at‑rest, TTL/удаление.
- [ ] Корректная работа с base64 для бинарного `store.db`.
